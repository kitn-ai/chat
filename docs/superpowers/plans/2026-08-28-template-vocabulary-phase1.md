> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to execute this plan. Work through the tasks in order — each task lands green on its own gates before the next starts. Mark each `- [ ]` checkbox `- [x]` as you complete it. **Goal.** Implement Phase 1 (tasks 1–5) of the template-registry + builder build: the net phase-1 construct vocabulary the T-5 rulings adopted (`aside` · `capabilities.messageActions` · `capabilities.sources` · `header.themeToggle`/`header.actions` · `composer.triggers` · `shell`) plus the kit tasks they depend on (`'speak'` as a real `ChatMessageAction`, per-role default action props, `hideSources`, `composerStart`/`composerEnd`), the codegen that emits every new key, and the `verify:construct` gate growth that keeps the new vocabulary covered end to end.

**Architecture.** Two leaf const modules (`src/elements/chat-actions.ts`, `src/ui/button-variant-names.ts`) become the single sources both the TS unions and the zod enums read (C-2: `schema.ts` compiles under `tsconfig.mcp.json`'s Node-only no-DOM pass, so it can never import `chat-types.ts` or a `.tsx` by value). Kit props land on `ChatThread` and thread through the `<kai-chat>` facade (React wrappers are GENERATED by `build:api` — never hand-edited). Schema additions are optional siblings under the existing `.strict()`/superRefine discipline. Codegen threads each new key onto ChatThread's real props or emits App-level chrome (shell palette/user menu, header buttons) per B-10. The gate (`verify-construct.mjs`) grows two ways: valuers for the two new capability keys (its existing hard-fail forces this) and a NEW derived top-level probe axis (C-5: `aside`/`header`/`composer`/`shell` are top-level keys the capability axis never synthesizes).

**Tech stack.** SolidJS · zod (schema single-source-of-truth, JSON Schema derived by `gen-construct-schema.mjs`) · vitest (`--project=unit`, jsdom) · Node .mjs gate scripts · pnpm + NX from the repo root.

**Spec.** `docs/superpowers/specs/2026-08-28-template-registry-and-builder-build.md` (Phase 1, rulings B-1..B-11, corrections C-1..C-5) — read alongside `docs/superpowers/specs/2026-08-28-t5-vocabulary-rulings.md`.

## Global constraints (bind every task)

- **`.strict()` everywhere; presence enables; cross-field rules in `superRefine` with loud path'd messages.** Widen, never restructure: every schema addition is an optional sibling; no existing key moves (B-1).
- **Every construct-authored string is `JSON.stringify`'d at its emit site** — never a raw JSX attribute string, never concatenated into CSS text. Closed schema enums (positions, variants, action ids) may interpolate directly, but B-3 pins the messageActions arrays to JSON.stringify anyway: the discipline is uniform, never value-dependent.
- **Derive, don't type.** The action-id list, the button-variant list, the gate's axes all READ their source (`chat-actions.ts`, `button-variant-names.ts`, the schema artifact). No number in any doc that a script can print — the gate prints its own cell counts.
- **Conventional commits** (release-please drives versioning; pre-1.0 so `feat!` = minor). Never hand-edit `package.json`'s version.
- **Run all commands from the repo root** unless a step says `cd packages/ui` (only `npm run build:api` and `npm run verify:construct` run inside `packages/ui`).
- **NX cache caveats (CLAUDE.md):** `nx build ui` can hit the cache and skip the derived-artifact generators while printing success — when artifacts must regenerate, use `npm run build:api` inside `packages/ui` or `--skip-nx-cache`. `nx typecheck ui`'s cached verdict has been wrong in both directions — trust `npm run typecheck` inside `packages/ui` or `nx typecheck ui --skip-nx-cache`.
- **`tsconfig.mcp.json` cannot see DOM.** `schema.ts`'s import graph must stay Node-clean: it may import the two new LEAF consts (no imports of their own) but never `chat-types.ts` (drags `tool-types`/`attachment-types`/`card-contract`) and never any `.tsx`.
- **`lint:silent-drops` is expected UNTOUCHED** (B-11d): nothing in phase 1 changes a `src/wire` discrimination. If you find yourself editing `src/wire`, STOP and surface it — that is a spec deviation, not something to waive.
- **Sequencing note:** the moment Task 3 regenerates the schema artifact with `messageActions`/`sources`, `verify:construct` hard-fails on the missing valuers **by design** (B-11a). Do not run `verify:construct` as a gate between Tasks 3 and 5; Task 5 closes it. Every other gate stays green per task.

  /**
   * Browser SpeechSynthesis mechanics, shared by `VoiceOutput`
   * (components/voice-output.tsx) and the message action bar's built-in
   * 'speak' action (primitives/message-feedback.ts) — ONE implementation, per
   * B-7's "back it with the existing kai-voice-output/SpeechSynthesis
   * mechanics". Free, local, no provider — no invoice concern.
   */

  /** True when the browser exposes the Web Speech synthesis API. */
  export function hasSpeechSynthesis(): boolean {
    return typeof window !== 'undefined' && 'speechSynthesis' in window;
  }

  /** Speak `text` natively: cancel-then-speak so a second call pre-empts the
   *  first (VoiceOutput's own speakNative discipline). No-ops where the API
   *  is absent (jsdom, some webviews) or `text` is empty — the caller's
   *  `kai-message-action` event still fires, so a host can back the same
   *  action with a model TTS path instead. */
  export function speakText(text: string): void {
    if (!hasSpeechSynthesis() || !text) return;
    window.speechSynthesis.cancel();
    window.speechSynthesis.speak(new SpeechSynthesisUtterance(text));
  }
