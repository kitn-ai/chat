# CLAUDE.md

Guidance for working **in this repo** with Claude Code. Consumer-facing usage lives in [README.md](README.md); the public docs are at <https://ui.kitn.ai>; the Claude Code tooling index is [`.claude/README.md`](.claude/README.md).

## What this is

`@kitn.ai/ui` — framework-agnostic, Shadow-DOM **web components** for building AI chat UIs (message threads, prompt input, streaming, markdown/code, reasoning + tool panels, attachments, generative-UI cards, artifacts). **Authored in SolidJS**, consumed from React / Vue / Svelte / Angular / plain HTML. Published to npm. The repo also ships the **`kai` MCP** (`packages/ui/src/agent-tooling/`) — a dev-time scaffolder that makes AI coding harnesses fluent at building with the library (`npx @kitn.ai/ui mcp`; tools: `scaffold` · `component_reference` · `theme` · `debug`).

## Architecture — two layers, Solid is the source of truth

- `packages/ui/src/primitives/` headless logic hooks + `ChatConfig` + on-demand highlighter · `packages/ui/src/ui/` in-house accessible UI primitives (no third-party UI deps) · `packages/ui/src/components/` the SolidJS AI feature components.
- `packages/ui/src/elements/` wraps coarse **`kai-*` web-component facades** over those via `defineWebComponent`; the elements bundle registers them (client-only — `register.ts` → `register-impl.ts`). `packages/ui/frameworks/react/` holds generated typed React wrappers (`@kitn.ai/ui/react`, exports `Chat`, `Message`, …).
- `packages/ui/src/state/` (`@kitn.ai/ui/state`) I/O-free pure folds over `ChatMessage[]`: `createAssistantStream`, `appendTextPart`/`appendReasoningPart`/`upsertToolPart` · `packages/ui/src/wire/` (`@kitn.ai/ui/wire`) the **model-stream adapter**: `readOpenAIStream` / `readAnthropicStream` / `readModelStream` parse provider SSE onto those parts, `toOpenAIMessages` / `toAnthropicMessages` encode the thread back. **The kit PARSES, the consumer FETCHES**, so there is no client, no key handling and no provider SDK below `wire/`. Never hand-roll an SSE reader in a doc, example or scaffold: import this one.
- `packages/ui/src/agent-tooling/` the `kai` MCP server + the integration/archetype catalogs — independent of the components.

## The `kai-` contract — do NOT get this wrong (it's what consumers hit)

- Elements are prefixed **`kai-`** (`<kai-chat>`). NEVER `kitn-` (a legacy prefix; the register-all bundle is `dist/kai.es.js`).
- **Array/object props** (`messages`, `suggestions`, `models`, …) are set as **JS properties**, never HTML attributes; only scalars (`placeholder`, `loading`, `theme`) work as attributes.
- Events are **non-bubbling `kai-*` CustomEvents** — listen on the element itself. Submit = **`kai-submit`**, read `event.detail.value`.
- Re-rendering needs a **new array reference AND a new object for each item that changed** — both, and not only while streaming. The array reference is what NOTIFIES (setting the same array back is a no-op even if you swapped an item inside it); the item's object identity is what makes the change VISIBLE, because the lists are reference-keyed `<For>`s. Adds, removes and reorders need only the fresh array; editing an existing item needs both. "New array per chunk" is the weaker rule and it is the one that shipped — it is what #224 followed before filing a bug. Pinned by `packages/ui/src/components/reactivity-contract.test.tsx`, whose stale-case assertions are each paired with an update case over the same harness so "nothing rendered" cannot pass vacuously.

## Build / test / dev

Run all commands from the **repo root** (pnpm + NX workspace):

```bash
pnpm install
pnpm dev             # Storybook (6006) + docs site (4321) together via nx run-many -t dev
nx build ui          # vite lib builds into packages/ui/dist/ (or pnpm build for all)
nx typecheck ui      # verify:quarantine, then the tsc passes in the package's `typecheck` script: Solid src + react wrappers + react tests + the Node MCP + tests/ and root tooling
pnpm --filter @kitn.ai/ui exec vitest run --project=unit     # jsdom unit suite; bare pnpm test / nx test ui also runs the emitted project + the flaky storybook browser project
pnpm --filter @kitn.ai/ui exec vitest run --project=emitted  # run-the-emitted-code guards: EXECUTES the scaffolder's emitted main.ts (seconds per file by construction — see below)
pnpm --filter @kitn.ai/ui run verify:scaffold  # compiles the MCP scaffolder's EMITTED code with tsc --strict (needs a build first)
```

- **A fresh clone or worktree needs THREE things before the unit suite means anything: `pnpm install`, then `build:css`, then a real build.** Skip any one and the suite fails in a way that reads like a broken checkout rather than a missing step, which is why this keeps costing time. **(1) `pnpm install`.** Worktrees live under `.claude/worktrees/` *inside* the parent checkout, so Node resolution walks up into the parent's `node_modules` while Vite only serves paths under the worktree root. The setup file is global to the project, so effectively the whole suite dies on one identical error: `Cannot find module '/@fs/<parent-checkout>/node_modules/@testing-library/jest-dom/dist/vitest.mjs'`. The file is really there; Vite is refusing to serve it from outside the root. `build:css` does not cover this and does not warn you, because `npm run` puts the ancestor `.bin` on PATH: it prints success and the suite still fails identically. Three agents read that as a broken checkout. **(2) `pnpm --filter @kitn.ai/ui run build:css`.** `src/elements/compiled.css` is generated and gitignored, so without it a large batch of files die on `Failed to resolve import "./compiled.css?inline"` and a couple more fail downstream assertions that need real styling. `nx build ui` and Storybook run it for you (`prebuild`); a bare `vitest` does not. **(3) A real build**, for `dist/custom-elements.json`. The MCP manifest tests now throw naming the exact path they wanted and how to produce it. That failure is new, and it is the *honest* version of an older green, not a tightening: resolution used to walk up ten parent directories and take the first `dist/custom-elements.json` it found, so from a worktree it escaped into the parent checkout and those tests PASSED, 16 of 17, against a six-week-old artifact from a tree nobody was working in. Never "fix" it by restoring the walk-up.
- **`--project=unit` is not the whole jsdom story.** The run-the-emitted-code guards live in their own `emitted` project: they write the scaffolder's emitted `src/main.ts` to a real module and EXECUTE it against a mounted `<kai-chat>`, which costs seconds per file by construction. **Its timings live in `packages/ui/emitted-code-tests.ts`, not here**, measured with `packages/ui/scripts/measure-timings.mjs`, which exists to re-run them on a quiet box — the pair this file used to quote was recorded on a box with four cores pinned by orphaned CPU burners left by a stale flake-hunting script, so no "idle" baseline from that window (Aug 11 22:10 to Aug 12 10:05 local) is idle, and the real numbers are LOWER, never higher. That correction belongs next to the budget it justifies, not copied across files. Before recording any timing anywhere, confirm the machine is quiet FIRST (`uptime`, plus a scan for processes pinning cores) rather than after one looks surprising. The project's per-test budget moved out of `test-timeout-budgets.ts` onto the project itself (`EMITTED_CODE_TIMEOUT`), so `unit` keeps vitest's one strict default. Both run in the required CI `test` job as separate steps, so a green `--project=unit` locally is not the merge gate: run `--project=emitted` too. `packages/ui/emitted-code-tests.ts` is the contract, and `tests/agent-tooling/emitted-project-wiring.test.ts` fails if CI stops invoking the project.
- **Two orderings in the typecheck chain are load-bearing, and both look like clutter.** `tsconfig.mcp.json` resolves `@kitn.ai/ui/schemas` to `./dist/schemas/index` *before* `./src/schemas/index`, so on a built tree CI checks the exact declarations a consumer is handed; `src` is only the fallback for an unbuilt tree, and pointing at `src` first was measured to take the pass from green to red. `verify:quarantine` runs *first*, ahead of the tsc passes, because the chain is `&&`-joined and the MCP pass is red on any unbuilt tree, so anywhere else in the order the rot check gets skipped on exactly the fresh clones where rot hides. Each is explained at its own site; read that comment before tidying either.
- **`nx build ui` CAN hit the NX cache and skip the derived-artifact generators** (`docs/web-components.md`, `packages/ui/llms-full.txt`, `packages/ui/src/elements/element-meta.json`), printing "Successfully ran target build" while changing nothing: those generators write their side effects into the SOURCE tree, and a cache restore does not put them back. That has been observed once and does not reproduce reliably (three consecutive runs afterwards all missed the cache and did regenerate), because the target's own source-tree side effects dirty its input hash, so a hit depends on what changed since the last build. **Rely on neither behaviour.** When you need the artifacts regenerated, use `npm run build:api` inside `packages/ui`, or `--skip-nx-cache`. **A cached build looks exactly like a successful one.**
- **`nx typecheck ui` is cached too, and its verdict has been wrong in both directions.** It printed success over `src/elements/slot-text.ts` while that file held a real TS1015 (`options?: {…} = {}`, "Parameter cannot have question mark and initializer"), and after the `?` was deleted the same command went on reporting that same error until the cache was bypassed. No pass was missing the file, so don't go hunting for a coverage gap. The greens worth trusting were `npm run typecheck` inside `packages/ui`, whose `verify:quarantine` step names it first, and `nx typecheck ui --skip-nx-cache`. Observed once and not pinned down; the stale red only costs time, **the cached green over broken code is the one that ships**.
- **Never run `gen-llms.mjs` standalone.** `build:api` already writes `llms-full.txt` from the model it parsed once; running the standalone generator afterwards silently rewrote it with LESS data — every slot's `inject`/`replace` collapsed to `—` across every row. The oversized diff was the only tell.
- `packages/ui/dist/` is a gitignored build artifact; `prepublishOnly` rebuilds it. The package ships **compiled** entry points (`.`, `./react`, `./elements`) — don't reintroduce raw-source exports.

## Testing the CONSUMER experience (not just internals)

`pnpm --filter @kitn.ai/ui exec vitest run --project=unit` is internal. To test what a consumer of the **published package** hits — packaging, exports, SSR, scaffold output, across every framework/integration — use the project skill **`/consumer-regression`** (`smoke` = one parallel pass + report; `regression` = the full build → triage → fix → re-verify loop). Unit tests catch none of those. See [`.claude/README.md`](.claude/README.md).

**Drive the published artifact, not the build.** A green CI says the tree compiles; it never says the thing a stranger installs works. A dotfile npm strips at publish, `npm pack --json` changing shape under a newer npm *during* the publish, a scaffold pinning a version an advisory covers — none was visible to any check over the tree, and each was visible within a minute of installing the published package and running it cold. **The tree is not the tarball, and the tarball is not what `npx` runs.** `docs/coupling-map.md` §1–§2 map what is unguarded between the tree, the tarball and the install.

Two cheap guards cover the same ground in the required CI job, and both are worth running locally before you push:

- `pnpm --filter @kitn.ai/ui run verify:consumer` packs the build, installs it into a throwaway app, bundles it with the Rolldown-based Vite that script pins (`VITE` in `scripts/verify-consumer-sideeffects.mjs`), and asserts every `kai-*` registration survives a real consumer bundler.
- `pnpm --filter @kitn.ai/ui run verify:scaffold` generates the scaffolder front ends — integrations × **surfaces** × TS frameworks, every axis derived from the registry rather than a hand-written list, so registering an integration moves the cell counts on its own — and compiles them with `tsc --strict --noUnusedLocals` across **three** tsc projects (default · angular, which needs `experimentalDecorators` + `noPropertyAccessFromIndexSignature` · solid, which needs `jsx: preserve` + `jsxImportSource`), resolving `@kitn.ai/ui` through the shipped exports map. **It prints the axes and cell counts it actually ran; read those, never a figure copied here.** **The surface axis is NOT the archetype list** — `listSurfaceProbes()` in `archetypes.ts` is each capability alone, plus none, plus all of them. The presets were the old axis and were a bad one: fewer distinct component lists than presets (`support-widget` repeats `drop-in-chat`'s), and every preset is exactly ONE capability, so the combinations the feature multi-select makes reachable — most of them — had nothing compiling them. Read the `WHY NOT THE POWER SET` comment at that function before changing the axis. It then adds **three** structural checks over what tsc cannot see: `html`, `angular`, and `solid`. The solid one asserts the emitted `renderPart` branches on every `MessagePart` variant, with the variant list derived from the union in `src/elements/chat-types.ts` rather than restated, because solid is the one framework that does not render through `<kai-chat>` and a `<Switch>` missing a `<Match>` compiles perfectly and renders nothing. Emitted code lives in string literals, so `scaffold.test.ts` can assert its wording but never its types. Run this after touching `agent-tooling/mcp/tools/scaffold.ts` or any integration route template. Needs `nx build ui` first.
- The same gate also compiles the **backend routes** (block 2), integrations × frameworks: the TypeScript routes, the python routes, and `mock`'s, which stream in the browser and emit no route at all. The TypeScript ones compile under three more tsc projects picked by the runtime the scaffolder declares, not by the framework asked for: `route-node` (express · Angular SSR · the Vite dev-server middleware — `types: ["node"]` and **no DOM**, a stock create-vite `tsconfig.node.json`) · `route-web` (Next · SvelteKit · TanStack Start, which ship DOM) · `route-worker` (`@cloudflare/workers-types` + node). The host typings are **real devDependencies** (`@sveltejs/kit`, `@tanstack/react-start`, `express`, `@cloudflare/workers-types`, `@angular/ssr`, `ai`, `@langchain/*`, `@mastra/client-js`) and must never be replaced by a `declare module` stub — a stub resolves the SDK calls to `any` and the gate goes back to proving nothing. Python routes get `ast.parse` + a structural SSE check. An unrecognised runtime label is a hard failure, so a new host cannot silently skip coverage.
- **Why the node/DOM split matters:** `request.json()` is `Promise<any>` under the DOM lib but `Promise<unknown>` under undici's, so a route that destructures it compiles in Next and fails `npm run build` in a stock Vite app. Emitted routes narrow it once via the injected `ChatRequestBody` / `readChatRequest` preamble; don't hand-roll a second one.

## Conventions

- **Copy/voice:** sound like a sharp human engineer, not AI-generated — follow `apps/docs/STYLE.md`. Web-components-FIRST framing; no emoji.
- **Versioning:** conventional commits drive **release-please** — never hand-edit the `package.json` version. Pre-1.0, so `feat!`/breaking = a minor bump.
- **Behaviors are prop/JSON-driven**, never CSS-manipulated or shadow-pierced.
- **Everything the model produced is untrusted input.** The threat model is not a hostile provider: an attacker only has to influence the model's OUTPUT, which retrieval over an untrusted document, a prompt injection, or a user asking a coding assistant about HTML all achieve against a perfectly trusted one. So a `MessagePart`, a card envelope or a tool argument reaching `innerHTML`, an `href`/`src`, `window.open` or an iframe is a vulnerability — and a card schema's `format: "uri"` constrains no scheme at all. The guards already exist: `isSafeUrl`/`SAFE_SCHEMES` (`src/primitives/card-routing.ts`) for anything navigable, `isRenderableLink` (`src/primitives/link-preview.ts`) for citations. Don't author a third policy; put an existing one on the sink. **The defect is never a missing guard, it is which path got it** — every one of them sat on a path the CONSUMER controls while the model-controlled path beside it had none. Copy the pattern in `tests/components/markdown-xss.test.tsx` and `artifact-url-xss.test.tsx` (`hostile-model-output.test.tsx` pins that the sink is the one every real message flows through): confirm each vector in a real Chromium before the fix, and assert the source text stays VISIBLE as well as inert — escaping is the correct rendering, and a filter that deleted the text would pass the security assertion while being a worse UI. Reporting and scope: [`SECURITY.md`](SECURITY.md).
- **The kit decides HOW; the app decides WHETHER.** How a message renders, how SSE parses, how focus moves, what the wire can represent, how a card validates — those are facts about the medium and this kit's own domain, and deciding them well IS the product. Whether this file is allowed, whether this user may do that, how much may be spent, what is retained, how many is too many — the consumer's call. Defaults are decisions, and good ones are most of what a component library is worth, so the test is not "is this a decision" but: **does this prop or default decide something that lands on an invoice or in a policy document?** If yes it belongs to the consumer — surface the fact they need (media type, byte size, whether the encoder can represent it) and let them decide. Limits, counts and quotas are application-layer decisions, not component-framework ones.
- **Corollary — decide loudly.** A silent drop, a silent truncation, a swallowed error, a silent fallback: each is a decision made while withholding the information that it happened. Deciding loudly is usually fine; deciding quietly almost never is.
  - Enforced on the one layer where the quiet version is irreversible, by `pnpm --filter @kitn.ai/ui run lint:silent-drops` (required CI, needs no build, ~1s). `src/wire` turns `parts` into a provider request, so a variant it does not encode is gone once the request leaves. A function there that discriminates a `MessagePart` at all must account for **every** variant — the list read from the union in `src/elements/chat-types.ts`, the same derivation `verify:scaffold` uses — or carry `// lint-silent-drops: drops <variants> -- <reason>` at the site. The waiver is a parsed directive and not prose **because prose already failed**: the turn that encoded an attachment to nothing (#186) shipped with a comment explaining the drop, so a guard honouring comments would have passed it unchanged. A waiver covers only the variants it names, which is what makes a seventh union member re-fire every waived site instead of being swallowed by a suppression written before it existed. Run `--self-test` to watch the analyzer detect.
- **A version literal nobody updates is a liability, even when the advice around it is right.** The docs correctly tell people to pin an exact version for CDN use (immutable, cacheable, SRI-able) — but each pin was hand-typed once while the kit kept releasing, so when a Critical advisory landed against a range of versions, copy-pasteable URLs in the docs *and in `packages/ui/README.md`, which npm renders on the package page*, were still serving versions inside it. **npm warns on installing a deprecated version; a CDN fetch warns about nothing**, so the channel with no safety net held the stalest pin. `pnpm --filter @kitn.ai/ui run lint:cdn-pins` (required CI, needs no build) asserts every `@kitn.ai/ui@<version>` literal under `apps/` · `packages/` · `examples/` · the root README **equals** `packages/ui/package.json`. Equality, not range membership — `^X` always contains `X`, so a range check is true by construction and can never fire. `fix:cdn-pins` rewrites them all when the version bumps. Lines narrating real past releases carry `lint-cdn-pins: historical -- <reason>` so a record is waived rather than rewritten into a falsehood; the repo-root `docs/` archive is out of scope for the same reason. A zero-match run is a hard failure here (unlike the object-URL guard), because it scans for pins the docs deliberately recommend.
- **Before generalising a fix into a rule, name a second instance of the class and check the rule against it** — if it only holds for the case you fixed, scope it to that case and say so. The second instance is nearly always already in the tree and cheap to check: "never import `@kitn.ai/ui/theme.css`" was the obvious lesson from a starter that shipped that file raw to a browser, which discards its Tailwind `@theme` block whole, but the Solid starter imports the same file safely because it runs Tailwind over it — the condition is whether Tailwind processes the file, not the import. **The wrong version is always the more quotable one**: the compression is what drops the qualifier that made it true, so a finding that shortens into something satisfying is exactly when to distrust it.
- **Derive it, don't type it.** Every defect involving a version, a path, a count or a list began as a hand-typed restatement of something the code already knew, and then the code moved. Read the fact where it lives; where a copy is unavoidable, record that it IS a copy — `docs/coupling-map.md` §4 registers the derived lists, and its unenforced list is where the remaining copies are. This is harder to keep than to state: `scripts/verify-scaffold-compiles.mjs`, the gate that derives every other axis from the registry, still carries a hand-written `FRAMEWORKS`.
  - **No number in this file that a script can produce.** Element/cell/route/test/row counts, timings and versions rot the moment the gate moves — a stale scaffold count survived here through a whole change of axis. Name the command or artifact that prints it instead. Ports, paths, event names and contract details are not measurements; they stay.
- Known consumer-packaging issues + their fixes: [`docs/package-consumer-issues.md`](docs/package-consumer-issues.md).
- **Before you change one side of anything, check what else moves:** [`docs/coupling-map.md`](docs/coupling-map.md) — every pair in this repo that depends on the other, what breaks, and which guard catches it (or `NOTHING`).
