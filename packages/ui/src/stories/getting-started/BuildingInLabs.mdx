# Building in the Labs

Labs is where compositions get prototyped and stress-tested before they become public docs. A lab wires real `kai-*` elements together the way a consumer would, to prove a slot, a part, or a new pattern composes. The composer showcase, the custom message thread, and the chat-slot demos all started here.

## Build a lab

A lab is a Storybook story titled under `Labs/…`. Add a `*.stories.tsx` in `src/elements/`:

```tsx
const meta = { title: 'Labs/My Composition' } satisfies Meta;
export default meta;

export const Demo = {
  render: () => {
    let el: HTMLElement | undefined;
    onMount(() => {
      if (!el) return;
      (el as any).items = [/* … */];                         // array/object data = JS property
      el.addEventListener('kai-select', (e) =>               // kai-* events are non-bubbling
        console.log((e as CustomEvent).detail));
    });
    return (
      <kai-prompt-input ref={(e) => (el = e as HTMLElement)}>
        <kai-menu slot="toolbar-start" trigger-icon="plus" />
      </kai-prompt-input>
    );
  },
};
```

The shadow boundary forces three rules, the same ones consumers hit:

- **Array/object data is a property**, set in `onMount`, not an attribute. Reassign a new reference to re-render; don't mutate in place.
- **Events are non-bubbling `kai-*` CustomEvents**: `addEventListener` on the element itself; Solid's `onClick`/`on:` don't cross the shadow root.
- **Slots take light-DOM children**: `<x slot="toolbar-start">` projects into the named region.

See `src/elements/composer-showcase.stories.tsx` or `labs-message-thread.stories.tsx` for fuller examples.

## Run and verify

```bash
npm run storybook   # http://localhost:6006
```

The `kai-*` elements inject `compiled.css`, built once at startup. A new element, a changed component class, or a new `@theme` token won't hot-reload, so restart Storybook (`lsof -ti:6006 | xargs kill; npm run storybook`). Preview CSS *does* hot-reload, which is misleading. Story files hot-reload fine.

The stronger version of the same trap, and it is not only CSS: **a `kai-*` story runs the last build, full stop.** `.storybook/preview.ts` imports `elementsReady` from the built `dist/kai.es.js`, that bundle registers every element, and it wins the `customElements.define` race. So the element you see is whatever `dist/` holds, no matter what the story imports or what you just changed in `src/elements/`. Editing a facade and reloading shows you the old element, silently and with no error. Rebuild (`nx build ui`) before you believe a facade story, and never take a dev-server fetch of your new source as evidence: the server can serve the new file to a page that is still running the old bundle. This has cost four people time in one day. Solid `Components/*` stories are the exception, since they import `src` directly and hot-reload normally, which is why the two tiers can disagree about the same component.

Solid `Components/*` stories render in the **light DOM** — no shadow root, so no injected `compiled.css`. What styles them is `.storybook/styles.css`, which `@import`s `src/elements/styles.css` — the same sheet `compiled.css` is built from. That import is the whole mechanism, and it is why a story and a `kai-*` element now agree: every `@layer components` rule (`.kai-radio`, `.kai-checkbox`, `.kai-range`, `.kai-focus-inset`), the focus ring and the scrollbars reach both. Before it, the Storybook sheet hand-copied a handful of those rules and silently omitted the rest, so three form controls rendered as raw OS chrome in every story while the shipped element rendered them fully designed — and two people in a row concluded from that the kit had unstyled controls. Add a rule to `src/elements/styles.css`; never copy one into the Storybook sheet.

What still cannot cross: `:host` selects nothing in the light DOM, so the host font/size defaults are re-stated on `body` in the Storybook sheet's shim, and anything you check that depends on shadow encapsulation has to be checked in a real `kai-*` story.

Check it both ways: toggle light/dark and confirm it holds at narrow widths; for anything interaction-driven, add a Playwright IVP rather than trusting the eye. The `tests/e2e/*-ivp.spec.ts` suites target stories by id (e.g. `labs-menu--plus-menu`) and assert real shadow-DOM behavior; run them with the matching `npm run test:*-ivp` script.

## Graduating a lab

When a composition is proven it gets promoted into the public docs at [ui.kitn.ai](https://ui.kitn.ai); the lab story stays here as the testing ground. Keep labs lean: they prove composition, they're not the consumer API reference.
